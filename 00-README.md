# Practice snapshot, package v1.0.1

Six files that describe how one intelligence architect works, at the level of ideas: what the practice believes, the vocabulary it uses, and the shape of a working session on evals. Written before any engagement it is used in, dated, and published so that the date can be checked by anyone.

| File | What it is |
|---|---|
| `00-README.md` | This file. |
| `01-practice-snapshot.md` | The practice in thirteen short sections. Each idea carries a `BG` id. |
| `02-provenance-manifest.md` | For every `BG` id: where the idea was first written down, when, and whether that evidence is public or private. Generated from the author's record. |
| `03-project-instructions.md` | Instructions for an assistant working in a project that holds these files beside a company's own material. Keeps the two apart. |
| `04-evals-workshop-shell.html` | A self-contained page for a working session on evals: a hero and fourteen one-idea sections, keyboard-driven, printable as a handout. Placeholder words and pictures, meant to be replaced. |
| `05-evals-workshop-shell-README.md` | How to swap a section, the caps, the keys, printing. |

## How to cite

An idea from the snapshot is cited by its id, for example "the definition of done for an encoded asset (BG-11)". The manifest is the record of what that id rests on. A deliverable that builds on an idea says so in its own words and cites the id; it does not copy the section.

## The boundary, in both directions

These files are the author's and predate any engagement they are used in. They carry no material belonging to any company the author works with, and nothing from them should be presented as created for one. In the other direction, a company's own methods, documents, customers and figures belong in that company's tools and never in a later version of this package. `03-project-instructions.md` holds the working rules.
